One install, a different loadout per terminal

Pick a profile to see what the launcher would mask for one session. The plugin names are made up. The mechanism is real and was tested: a generated --settings file sets enabledPlugins to false for every installed plugin the profile doesn't list.







Use case 1: Profiles
Plugins, skills and MCP servers are installed globally, so every session carries all of them. Want: named profiles (frontend, SRE, SEO...) that differ per terminal, concurrently.


Use case 2: Discoverability
In a company with ~50 internal plugins in a git marketplace, people can't tell what exists, what to use when, what overlaps, what's new, or who owns it.




Bottom line. Both problems are real but narrower than they first look. Native features cover much of each. The unserved parts are: default-deny and composable named profiles (launcher), and a derived catalog with ownership/status/overlap/new-since views (catalog). Build both thin, in one repo, as independent modules sharing a small core/.


Key facts that shaped the plan


    

  • The "42k tokens of skills" pain is probably outdated: the listing is capped at 1% of context and MCP tools are deferred. What remains is routing quality and clutter. V

  • enabledPlugins and skillOverrides work inside a --settings file; shell aliases already cover ~80-90% of profile needs. V/R
    • 

  • disableSideloadFlags can kill --plugin-dir, --agents, --mcp-config; managed force-enabled plugins can't be masked. The launcher must detect policy, not bypass it. V
    • 

  • Bundles (a plugin with only dependencies) are native; metadata in marketplace.json is not read or rendered by Claude Code. V
    • 

  • Keychain auth is per CLAUDE_CONFIG_DIR, so config-dir-per-profile means a login per profile. V

Adversary's ranked objections


1. Launcher is least useful in locked-down orgs
Those orgs (disableSideloadFlags, managed force-enables) tend to have the biggest marketplaces.


2. "Shared core" is thin
About 200 lines of marketplace.json parsing: weak ground for calling it one product. Resolution: shared core/, independent modules.


3. Native features and upstream are closing the gap
Relevance, /skill-doctor, Stats tab, installCount, Analytics API. Faceted Discover is plausible next. Build only what's cheap to delete.


4. Metadata drift
Any field without a CI gate rots. Derive the catalog; never a second source of truth.


5. Adoption
Users live in /plugin. Link a web page from the README and push recommendations via relevance blocks.


6. Security
Launcher must detect policy and say "blocked by policy", never work around it, especially when the user governs the org's policy.

Recommendation & roadmap


One repo, three modules.

core/      read marketplace.json + installed state, resolve sets (pure)
profiles/  local per-terminal launcher           (depends on core)
catalog/   metadata lint + static site, run in CI (depends on core)


Bridge: profile = bundle plugin, so catalog-published bundles become selectable profiles.


Principles


    

  • Never write shared state; write only content-addressed files in the launcher's own cache dir and start claude (spawn and wait, so it works on Windows).
    • 

  • Respect org policy; report "blocked by policy".
    • 

  • Prefer --settings masking + skillOverrides over sideload flags.
    • 

  • Everything cheap to delete; launcher thin enough to drop if native profiles ship (#91770).
    • 

  • Lead the pitch with routing quality and clutter, not tokens.

How the launcher invokes Claude Code


    

  1. Resolve the profile: sources, extends, one resolved profile.
    2. 

  2. Look at the machine (read-only): claude --version, claude plugin list --json, policy signals; report plugins not installed.
    3. 

  3. Compile content-addressed files in the launcher's cache dir: a settings file (enabledPlugins false for everything not in the profile, skillOverrides, env/model) and, if strict, an MCP config.
    4. 

  4. Build the command line: claude --settings <file> [--strict-mcp-config --mcp-config <file>] [--model ...] <your passthrough args>; --setting-sources project,local when inherit_user_settings = false.
    5. 

  5. Spawn and step aside: inherited TTY, launcher ignores Ctrl+C, forwards termination, returns Claude's exit code. It never proxies the conversation.
    6. 

  6. Write nothing shared (~/.claude, ~/.claude.json, plugin cache).
    7. 



What profiles share, and combining with accounts


No CLAUDE_CONFIG_DIR is set, so all profiles share auth (tested), projects and trust, session history (mixed in /resume), auto memory and CLAUDE.md (decided: fine), user settings by default, the plugin cache, and claude.ai connector auth. A profile is a loading filter, not a security or identity boundary. A repo's own .mcp.json, .claude/ skills/agents/settings still apply.


Profiles and accounts are two axes. A profile chooses what is active; an account (a separate CLAUDE_CONFIG_DIR) chooses the identity and data dir. Ways to combine:

  1. Honor the environment: CLAUDE_CONFIG_DIR=~/.claude-work cprof run sre works from day one; the launcher must never override that variable, and its plugin-list call runs under it.
    2. 

  2. Built-in accounts: [accounts.work] config_dir = "~/.claude-work" in config; cprof run sre --account personal; a profile may pin account; cprof account add prints the one-time /login steps and never touches credentials.
    3. 

  3. Delegate to an existing config-dir switcher and run cprof inside it.

Per account: plugins and marketplaces are installed separately, the plugin cache is duplicated (don't symlink plugins/; CLAUDE_CODE_PLUGIN_SEED_DIR untested), each account has its own login, managed settings still apply, and org profiles are shared via the profile sources. To test under a second config dir, a human must do the interactive login first. Details in 07-how-it-invokes-claude.md.

R2: support both GHE Cloud and GHE Server. Design to the lowest common denominator:

    

  • CLI first, workflow second: all logic in the Go binary, the Actions workflow is a thin wrapper, so the same binary runs in any CI.
    • 

  • No hard-coded hosts; use GITHUB_SERVER_URL / GITHUB_API_URL or config; test against a non-github.com host.
    • 

  • Minimal third-party actions; where needed (setup-go, pages upload) document mirroring/allowlisting on GHE Server and offer an alternative.
    • 

  • Offline-tolerant: binary from the internal instance, no runtime fetches from github.com, catalog site fully self-contained (no CDN).
    • 

  • Version skew: avoid or make optional newer Actions syntax, artifact attestations and some Pages options; record a minimum Server version.
    • 

  • Auth via the user's git credential helper / SSH, GITHUB_TOKEN in CI; no stored tokens.
    • 

  • Catalog output is a plain static directory; Pages is one publish option.
    • 



Go choices: one module with core/profiles/catalog packages and one binary; TOML library; JSON Schema validation; shell out to the user's git; static HTML + small vanilla JS for the catalog; goreleaser; CI matrix on macOS, Ubuntu and Windows; golden-file tests with a fake claude.


Cross-platform requirement (R1)


The tooling must work on macOS, Linux (WSL counts as Linux) and native Windows with the same profile files. Stage 0 ran on macOS only; Linux and Windows behavior is untested.


AreaChange from the Unix-only draft


Starting claudeNo exec on Windows: spawn a child, ignore Ctrl+C in the launcher, forward termination, return the exit code.


Generated filesContent-addressed files in the launcher's cache dir (name = hash of the resolved config): concurrent runs never collide, no cleanup problem, no overwriting open files on Windows. Atomic write, GC at launch.


Finding claudePATH lookup (.exe/.cmd), fallback ~/.local/bin, override option.


PathsAccept ~ and forward slashes, normalize backslashes, write forward slashes into generated JSON. Launcher dirs: XDG or ~/.config on Unix, %APPDATA% / %LOCALAPPDATA% on Windows.


Shortcutsshell-init for bash, zsh, fish, pwsh; .cmd shims for cmd. Never depend on symlinks (Windows needs Developer Mode).


MCP npx serversPer-OS command override in the MCP registry. Whether native Windows needs cmd /c is unverified (docs agent said no; my recollection says yes).


Policy detectionManaged-settings paths are known per OS; Windows registry/MDM and server-managed settings are not readable reliably, so also detect by failure (exit 1 on a sideload flag).


CredentialsLinux/Windows keep .credentials.json inside the config dir with no documented locking; concurrent refresh is untested there.


EncodingWrite UTF-8 no BOM + LF; read tolerant of BOM/CRLF; reject UTF-16 (PowerShell 5 redirection) clearly.


DistributionNo self-update (running .exe can't be replaced); Homebrew, Scoop/WinGet, release downloads; signing/notarization or SmartScreen friction.


TestingCI matrix on macOS, Ubuntu, Windows with a fake claude test double; real-claude test opt-in.




Supported targets, first release: darwin/arm64, darwin/amd64, linux/amd64, linux/arm64, windows/amd64, windows/arm64. goreleaser builds all six; unit and fake-claude tests run natively where hosted runners exist (arm64 runners for public repos need verification; otherwise compile-checked and marked "built, not natively tested"). Publish via Homebrew, Scoop and WinGet; signing/notarization or package-manager coverage required. The real-claude test stays opt-in.


Strengthens Go (os/exec, build tags, cross-compilation, goreleaser to Homebrew/Scoop/WinGet). TypeScript with bun --compile is possible; Windows console handling is the weaker spot.


Profile sources and sharing


Claude Code has no native profile repo: marketplaces distribute plugins, and a bundle distributes "which plugins go together" but not masking, MCP definitions or session defaults. Profiles need their own path.


SourceHowNotes


plugin (planned after dir and git)Data-only plugin (e.g. org-profiles@acme) holding profiles/*.toml; found via claude plugin list --json.Reuses native auth, pinning, autoUpdate, strictKnownMarketplaces. Must be installed and never masked. Untested under policy.


gitLauncher clones a repo at a pinned ref into a cache.Works for a profiles-only repo; adds its own fetch/auth path.


dirPersonal dir or .claude-profile/ in a project repo.Always available.




Precedence: personal, then project, then org; extends can still pull in org profiles.


[[sources]]
type = "dir"
path = "~/.config/claude-profile/profiles"      # personal

[[sources]]
type = "plugin"
plugin = "org-profiles@acme"                    # org profiles shipped as a plugin
path = "profiles"

[trust]
require_pin = true     # refuse git sources without a pinned ref
on_change = "prompt"   # prompt | fail | allow, when a profile adds MCP commands, env or prompt text


Trust. A shared profile can define MCP commands, env and system-prompt text, so loading one is effectively running code from that source. The launcher loads org profiles only from sources the org already trusts, records hashes in a lockfile, shows a diff and asks before accepting risky changes (cprof trust), and never bypasses org policy.


Manifest sketch (annotated)


Design proposal; field names are not final. One file per profile; the file name must match name.


# ---- Identity (shown in ls, search, and the catalog page) ----
name = "frontend"             # Unique id, kebab-case. What you type: `cprof run frontend`.
                              # Also the name of the generated bundle plugin profile-frontend.
description = "React, CSS and accessibility work"   # One line, shown in listings and the catalog.
owner = "@web-platform"       # Team or person who maintains it. Required for org profiles
                              # (CI lint); optional for personal ones.
status = "active"             # active | experimental | deprecated. Deprecated profiles still
                              # run but warn and point to superseded_by.
superseded_by = ""            # Only when deprecated: the replacement profile.

# ---- Account (optional) ----
account = ""                  # Default account (separate CLAUDE_CONFIG_DIR) for this profile.
                              # Precedence: --account flag, this field, config default_account,
                              # then Claude Code's default dir. Empty = the default dir.

# ---- Composition ----
extends = ["base"]            # Parents, applied in order. Lists are unioned; a later off or
                              # exclude beats an earlier include. Cycles are an error.

# ---- Discovery hints (used by search, recommend, and the catalog) ----
when_to_use = ["UI components", "visual QA"]   # Tasks this profile fits.
avoid_when  = ["infra changes"]                # Tasks it does not fit.

# ---- Plugins ----
[plugins]
mode = "allow-only"           # allow-only (default-deny): every installed plugin not listed is
                              #   masked with enabledPlugins:false, regenerated on each launch
                              #   so newly installed plugins stay off.
                              # additive: only plugins in exclude are masked.
include = ["design-kit@acme", "playwright@acme"]   # name@marketplace; dependencies are followed,
                              # so a bundle brings its parts.
exclude = []                  # Always masked, even if a parent included them.

# ---- Standalone skills (~/.claude/skills; NOT plugin skills) ----
[skills]
off = ["legacy-helper"]       # Hidden via skillOverrides "off". Plugin skills can only be
                              # controlled per whole plugin, so use [plugins] for those.
name_only = ["docs-writer"]   # Name visible, description dropped (smaller listing).

# ---- MCP servers ----
[mcp]
servers = ["figma"]           # Names resolved from an MCP registry file; become the per-session
                              # --mcp-config.
claudeai_connectors = "none"  # none | keep. Connectors ignore enabledPlugins; "none" needs
                              # --strict-mcp-config, which org policy can block.
strict = true                 # Pass --strict-mcp-config so only the servers above load.

# ---- Session defaults ----
[session]
model = "opus"                # Model for this profile (optional).
effort = "high"               # low | medium | high | xhigh | max (optional).
append_system_prompt_file = "prompts/frontend.md"   # Appended to the system prompt.
inherit_user_settings = true  # true: keep ~/.claude/settings.json, mask plugins per key.
                              # false: --setting-sources project,local (drops user plugins,
                              # skills, MCP, hooks, model); re-add only what the profile sets.
[session.env]
FIGMA_TOKEN_REF = "op://dev/figma/token"   # Prefer secret-store references over raw values.
                              # Never commit secrets.

# ---- Policy behavior ----
[policy]
on_blocked = "warn"           # warn | fail. What to do when org policy blocks something the
                              # profile needs. The launcher never bypasses policy.

    2.
