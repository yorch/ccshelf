One install, a different loadout per terminal

Pick a profile to see what the launcher would mask for one session. The plugin names are made up. The masking mechanism was tested on macOS (reported by a subagent): a generated --settings file sets enabledPlugins to false for every installed plugin the profile doesn't list. Writing true for the kept plugins and the policy toggle below are design intent, not tested.







Use case 1: Profiles
Plugins, skills and MCP servers are installed globally, so every session carries all of them. Want: named profiles (frontend, SRE, SEO...) that differ per terminal, concurrently.


Use case 2: Discoverability
In a company with ~50 internal plugins in a git marketplace, people can't tell what exists, what to use when, what overlaps, what's new, or who owns it.




Bottom line. Both problems are real but narrower than they first look. Native features cover much of each. The unserved parts are: default-deny and composable named profiles (launcher), and a derived catalog with ownership/status/overlap/new-since views (catalog). Build both thin, in the tool repo, as three Go packages (core, profiles, catalog) in one binary, where profiles and catalog depend only on the small shared core.


Key facts that shaped the plan


    

  • The "42k tokens of skills" pain is probably outdated: the listing is capped at 1% of context and MCP tools are deferred V. What remains is routing quality and clutter, but that benefit is an inference and has not been measured U.
    • 

  • enabledPlugins and skillOverrides work inside a --settings file; shell aliases already cover roughly 80-90% of profile needs (the adversary's estimate). R
    • 

  • disableSideloadFlags can kill --plugin-dir, --agents, --mcp-config; managed force-enabled plugins can't be masked. The launcher must detect policy, not bypass it. V
    • 

  • Bundles (a plugin with only dependencies) are native; metadata in marketplace.json is not read by Claude Code, so nothing renders it and the catalog must. V
    • 

  • Keychain auth is per CLAUDE_CONFIG_DIR on macOS (a credentials file inside the config dir on Linux and Windows), so config-dir-per-profile means a login per profile. V
    • 

  • The project name claude-profile carries a brand risk ("Claude" in an open-source tool's name) and an existing Go tool already uses it. Accepted for now; revisit before a public release.

Adversary's ranked objections


1. Launcher is least useful in locked-down orgs
Those orgs (disableSideloadFlags, managed force-enables) tend to have the biggest marketplaces.


2. "Shared core" is thin
About 200 lines of marketplace.json parsing: weak ground for calling it one product. Resolution: shared core/, independent modules.


3. Native features and upstream are closing the gap
Relevance, /skill-doctor, Stats tab, installCount, Analytics API. Faceted Discover is plausible next. Build only what's cheap to delete.


4. Metadata drift
Any field without a CI gate rots. Derive the catalog; never a second source of truth.


5. Adoption
Users live in /plugin. Link a web page from the README and push recommendations via relevance blocks.


6. Security
Launcher must detect policy and say "blocked by policy", never work around it, especially when the user governs the org's policy.

Reconciling "one project"


    

  • Brainstorm: one manifest is the shared core (a profile is a curated set; a catalog entry is a curated "what to use for X").
    • 

  • Adversary: mostly a rationalization; lifecycles differ (local ephemeral per-terminal vs org-published, versioned, reviewed), trust models conflict, and bundles are install-side, not per-session subtraction.
    • 

  • Adopted: one repo, independent modules sharing a small core/; a profile bundle is the bridge, so catalog-published bundles become selectable profiles.
    • 



When is a custom catalog worth it?


Reference points from the adversary: about 20 plugins needs nothing beyond native features plus a generated README table; about 100 makes a static page with facets worth building; about 500 needs a governed registry. The custom-catalog threshold is roughly 50 to 80 plugins, or more than one publishing team. Your ~50 is at the threshold.

Principles


    

  • Never write shared state; write only content-addressed files in the launcher's own cache dir and start claude (spawn and wait, so it works on Windows).
    • 

  • Respect org policy; report "blocked by policy".
    • 

  • Prefer --settings masking + skillOverrides over sideload flags (--plugin-dir, --agents, --mcp-config), which policy can disable; use them only when allowed.
    • 

  • Everything cheap to delete; launcher thin enough to drop if native profiles ship (#91770).
    • 

  • The catalog is derived, never a second source of truth: marketplace.json + per-plugin sidecar files + git data.
    • 

  • Lead the pitch with routing quality and clutter, not tokens.
    •

Design: invocation, sources and manifest


How the launcher runs Claude Code, what profiles share, where profile files come from, and the manifest and CLI sketches. Design proposals; names are provisional.


How the launcher invokes Claude Code


    

  1. Resolve the profile: sources, extends, one resolved profile.
    2. 

  2. Look at the machine (read-only): claude --version, claude plugin list --json (--available when the catalog needs uninstalled plugins), policy signals; report plugins not installed.
    3. 

  3. Compile content-addressed files in the launcher's cache dir: a settings file (enabledPlugins false for everything not in the profile, skillOverrides, env/model) and, if strict, an MCP config.
    4. 

  4. Build the command line: claude --settings <file> [--strict-mcp-config --mcp-config <file>] [--model ...] <your passthrough args>; --setting-sources project,local when inherit_user_settings = false.
    5. 

  5. Spawn and step aside: inherited TTY, launcher ignores Ctrl+C, forwards termination, returns Claude's exit code. It never proxies the conversation.
    6. 

  6. Write nothing shared (~/.claude, ~/.claude.json, plugin cache).
    7. 



Also: --effort is passed when the profile sets it; the system-prompt addition is passed as text via --append-system-prompt (a file-based flag was not verified); if policy blocks a flag, behavior follows [policy] on_blocked (warn drops that part, fail refuses). Two terminals produce two command lines pointing at two immutable files (tested on macOS with three parallel sessions). What breaks if Claude Code changes: the design depends on --settings honoring enabledPlugins and skillOverrides, on --strict-mcp-config and on claude plugin list --json; gate on claude --version and run the real-claude init-event test in CI against new releases.


What profiles share, and combining with accounts


No CLAUDE_CONFIG_DIR is set, so all profiles share auth (tested), projects and trust, session history (mixed in /resume), auto memory and CLAUDE.md (decided: fine), user settings by default, the plugin cache, and claude.ai connector auth. A profile is a loading filter, not a security or identity boundary. A repo's own .claude/ skills, agents and settings still apply, and so does its .mcp.json unless the profile uses strict.


Profiles and accounts are two axes. A profile chooses what is active; an account (a separate CLAUDE_CONFIG_DIR) chooses the identity and data dir. Ways to combine:

  1. Honor the environment: CLAUDE_CONFIG_DIR=~/.claude-work cprof run sre works from day one; the launcher must never override that variable, and its plugin-list call runs under it.
    2. 

  2. Built-in accounts: [accounts.work] config_dir = "~/.claude-work" in config; cprof run sre --account personal; a profile may pin account; cprof account add prints the one-time /login steps and never touches credentials.
    3. 

  3. Delegate to an existing config-dir switcher and run cprof inside it.

Per account: plugins and marketplaces are installed separately, the plugin cache is duplicated (don't symlink plugins/; CLAUDE_CODE_PLUGIN_SEED_DIR untested), each account has its own login, managed settings still apply, and org profiles are shared via the profile sources. To test under a second config dir, a human must do the interactive login first. Details in 07-how-it-invokes-claude.md.

Trust. A shared profile can define MCP commands, env and system-prompt text, so loading one is effectively running code from that source. The launcher loads org profiles only from sources the org already trusts, records hashes in a lockfile, shows a diff and asks before accepting risky changes (cprof trust), and never bypasses org policy.


Still undecided: whether the data-only plugin approach works smoothly under strictKnownMarketplaces or other policy (untested), and how a profile that lists an uninstalled plugin is reported (current design: report it and print the install command; never install silently).


Manifest sketch (annotated)


Design proposal; field names are not final. One file per profile; the file name must match name.


# ---- Identity (shown in ls, search, and the catalog page) ----
name = "frontend"             # Unique id, kebab-case. What you type: `cprof run frontend`.
                              # Also the name of the generated bundle plugin profile-frontend.
description = "React, CSS and accessibility work"   # One line, shown in listings and the catalog.
owner = "@web-platform"       # Team or person who maintains it. Required for org profiles
                              # (CI lint); optional for personal ones.
status = "active"             # active | experimental | deprecated. Deprecated profiles still
                              # run but warn and point to superseded_by.
superseded_by = ""            # Only when deprecated: the replacement profile.

# ---- Account (optional) ----
account = ""                  # Default account (separate CLAUDE_CONFIG_DIR) for this profile.
                              # Precedence: --account flag, this field, config default_account,
                              # then Claude Code's default dir. Empty = the default dir.

# ---- Composition ----
extends = ["base"]            # Parents, applied in order. Lists are unioned; a later off or
                              # exclude beats an earlier include. Cycles are an error.

# ---- Discovery hints (used by search, recommend, and the catalog) ----
when_to_use = ["UI components", "visual QA"]   # Tasks this profile fits.
avoid_when  = ["infra changes"]                # Tasks it does not fit.

# ---- Plugins ----
[plugins]
mode = "allow-only"           # allow-only (default-deny): every installed plugin not listed is
                              #   masked with enabledPlugins:false, regenerated on each launch
                              #   so newly installed plugins stay off.
                              # additive: only plugins in exclude are masked.
include = ["design-kit@acme", "playwright@acme"]   # name@marketplace; dependencies are followed,
                              # so a bundle brings its parts.
exclude = []                  # Always masked, even if a parent included them.

# ---- Standalone skills (~/.claude/skills; NOT plugin skills) ----
[skills]
off = ["legacy-helper"]       # Hidden via skillOverrides "off". Plugin skills can only be
                              # controlled per whole plugin, so use [plugins] for those.
name_only = ["docs-writer"]   # Name visible, description dropped (smaller listing).

# ---- MCP servers ----
[mcp]
servers = ["figma"]           # Names resolved from an MCP registry file; become the per-session
                              # --mcp-config.
claudeai_connectors = "none"  # none | keep. Connectors ignore enabledPlugins; "none" needs
                              # --strict-mcp-config, which org policy can block.
strict = true                 # Pass --strict-mcp-config so only the servers above load.

# ---- Session defaults ----
[session]
model = "opus"                # Model for this profile (optional).
effort = "high"               # low | medium | high | xhigh | max (optional).
append_system_prompt_file = "prompts/frontend.md"   # Appended to the system prompt.
inherit_user_settings = true  # true: keep ~/.claude/settings.json, mask plugins per key.
                              # false: --setting-sources project,local (drops user plugins,
                              # skills, MCP, hooks, model); re-add only what the profile sets.
[session.env]
FIGMA_TOKEN_REF = "op://dev/figma/token"   # Prefer secret-store references over raw values.
                              # Never commit secrets.

# ---- Policy behavior ----
[policy]
on_blocked = "warn"           # warn | fail. What to do when org policy blocks something the
                              # profile needs. The launcher never bypasses policy.

Decided: a metadata sidecar per plugin. With ~50 plugins in one marketplace.json, CODEOWNERS can't route review per JSON entry, so "authors write, platform team reviews" can't be enforced by file ownership. Listing several owners on one CODEOWNERS line requires approval from any one of them; requiring both teams needs branch protection or rulesets. lint can check that every plugin folder has a CODEOWNERS line and that the sidecar owner matches it.


Generated bundles. compile writes bundles/profile-<name>/.claude-plugin/plugin.json (name, version, dependencies). They are committed because marketplaces serve files from git; CI runs compile --check and fails on drift. The bundle's marketplace.json entry is hand-written once and lint checks every profile has an entry and every bundle entry has a profile (generating those entries into marketplace.json was rejected: mixing generated and hand-written entries invites merge conflicts).


Consumption. Plugins: add the marketplace natively; bundles install a profile's set in one step. Profiles: a git source pinned to a tag of this repo, or a local clone as a dir source (plugin source later). Catalog: the published site, plus search and doctor reading the same data locally.


Variants. Plugins in other repos use a git source and still get a sidecar here; several teams can keep separate marketplace repos feeding one catalog build; a public data repo is possible (R4 then applies to the data).


Open: whether the catalog also commits a readable CATALOG.md; an extra review path in lint for plugins that bundle MCP servers or hooks (they run code); release cadence and naming for repo tags.

Cross-platform requirement (R1)


The tooling must work on macOS, Linux (WSL counts as Linux) and native Windows with the same profile files. Stage 0 ran on macOS only; Linux and Windows behavior is untested.


Facts from the docs (reported by a research agent; the Windows registry/MDM details were truncated):


    

  • Native Windows: %USERPROFILE%\.local\bin\claude.exe (PowerShell/CMD installer or WinGet) or npm (Node 22+). The shell tool is PowerShell; Git Bash is optional (CLAUDE_CODE_GIT_BASH_PATH). WSL is a separate Linux install with its own ~/.claude.
    • 

  • Config is ~/.claude/ and ~/.claude.json (%USERPROFILE% on Windows); Linux does not use XDG for Claude Code.
    • 

  • Managed settings: macOS /Library/Application Support/ClaudeCode/, Linux /etc/claude-code/, Windows C:\Program Files\ClaudeCode\; registry/MDM/GPO is mentioned but not detailed.
    • 

  • Credentials: macOS Keychain (per config dir, file fallback); Linux and Windows use <config dir>/.credentials.json with no documented locking.
    • 

  • JSON settings and MCP configs use forward slashes everywhere, with ~ and ${VAR} expansion; CLAUDE_CODE_PLUGIN_DIRS uses : on Unix and ; on Windows. Claude Code has no temp-dir override (TMPDIR, or TEMP/TMP on Windows).
    • 

  • Symlinks on Windows need Developer Mode or admin; WinGet upgrades can fail while claude.exe runs.
    •

What it means for the design


    

  1. Masking via --settings works and is per key, so subtracting plugins doesn't need --setting-sources. The launcher needs the installed list (claude plugin list --json) to build a default-deny map and must regenerate it each run.
    2. 

  2. --setting-sources project,local is a blunt but real default-deny for the user layer and keeps auth, but it also drops user model, hooks, statusline and synced-scope plugins, so the launcher must re-add what matters through --settings.
    3. 

  3. claude.ai connectors ignore enabledPlugins; only --strict-mcp-config removes them, and that depends on --mcp-config, which disableSideloadFlags can block.
    4. 

  4. skillOverrides only helps for standalone skills; plugin skills are controlled per whole plugin.
    5. 

  5. Concurrency looked safe for per-session generated settings; the launcher must never touch ~/.claude.json.
    6. 

  6. No managed policy on this machine, so locked-down behavior is unvalidated.
    7.

Glossary


These terms mean the same thing in every note and in this report.


TermMeaning


ProfileA named recipe (profiles/<name>.toml) saying which plugins, standalone skills and MCP servers are active for one Claude Code session, plus session defaults. Started with cprof run <name>. It filters what is already installed; it is not an identity or security boundary. Part of the launcher (use case 1).


Profile bundleA generated, dependency-only plugin named profile-<name>, kept in bundles/, so a profile's plugins install natively with one /plugin install. It is not itself a profile.


CatalogA generated, browsable index of an org's plugins and profiles: a static site plus catalog.json, built in CI from marketplace.json, the sidecars and git data, and queryable locally with search and doctor. Not committed. Answers what exists, which to use and who owns it (use case 2).


SidecarThe per-plugin catalog metadata file catalog/plugins/<name>.toml (owner, status, when_to_use, overlaps, review date).


MarketplaceThe Claude Code concept: a git repo with .claude-plugin/marketplace.json and plugins that Claude Code installs from. Not the catalog, which is a richer view built on top of it.


Tool repoThis public repo: Go source, schemas, docs, releases, the reusable Action and a starter template. Never holds org data.


Org data repoAn adopting org's private repo (GHE Cloud or Server) holding its marketplace, plugins, profiles, sidecars, org config and CI. Also called the profile catalog repo in conversation.


AccountA Claude Code identity and data directory (a separate CLAUDE_CONFIG_DIR). An independent axis from profiles.


Profile sourceWhere profile files come from: dir, git (first release) and later plugin. Config key [[sources]] in the user's config.toml.


MaskingSetting enabledPlugins: false in a generated --settings file for every installed plugin the profile doesn't list.


CapabilityOne thing the launcher needs from Claude Code (settings masking, strict MCP config, --plugin-dir, ...). It probes each and degrades per feature when managed policy blocks it.


ModulesThe three Go packages in the tool repo: profiles/ (launcher), core/ (shared parsing and resolution) and catalog/.
