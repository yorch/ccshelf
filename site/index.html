One shelf of plugins. A different loadout for every terminal.

ccshelf starts Claude Code with only the plugins, skills and MCP servers that a named profile asks for. Run ccshelf run sre in one terminal and ccshelf run frontend in another, at the same time.

Status: implemented and under review, not released yet. Tested on macOS and Linux; Windows runs in CI and is best-effort until proven. Install from source for now. Open source (MIT). Unofficial: not affiliated with Anthropic.

Every terminal does not need every plugin

An organization with around fifty internal plugins ends up with a crowded session: skills for incident response sit next to skills for CSS, and nobody can say which plugin a task should use. Claude Code enables plugins through settings, so the set you choose is usually the set every session starts with.

ccshelf adds two things. A launcher that chooses the set per terminal, and a catalog that answers "what exists, which should I use, who owns it" from metadata the organization already keeps in git.

What has been measured so far: in one run on one real setup, hiding MCP servers and claude.ai connectors through the generated settings cut about 5.7k input tokens (19%, from 29.7k to 24.0k). That is a single run, not a benchmark. Whether a smaller set also improves how often the right skill fires is the open Phase 0 routing evaluation. Details in docs/research/stage0.md.

How it works

A profile never installs anything. It switches off what it does not list, for one session.

One shared store

  • installed plugins
  • login
  • session history
  • memory

Your normal Claude Code config. ccshelf never writes it.

ccshelf

  • resolve the profile
  • mask what it does not list
  • validate the result
  • write settings-<hash>.json

Files are named by content hash and written to its own cache.

Terminal A

claude --settings a1…

sre loadout

Terminal B

claude --settings 7f…

frontend loadout

  1. Resolve. Read the profile, follow its extends, and list what is installed with claude plugin list --json. Plugins a profile names but you lack are reported with the install command; nothing is installed silently.
  2. Compile. Write a settings file that sets enabledPlugins to false for every installed plugin the profile does not list. It is regenerated on each run, so a plugin you install tomorrow does not leak in. The same file can hide claude.ai connectors and named MCP servers.
  3. Validate. Claude Code ignores an invalid settings file without a message, so ccshelf checks the generated JSON against a closed schema before every launch.
  4. Start. On macOS and Linux ccshelf replaces itself with claude using exec, so job control and exit codes are exactly those of plain claude. On Windows it starts claude and waits.

Shared by every profile

Login, session history, auto memory, CLAUDE.md and the plugin cache. There is one copy of each plugin; profiles only change what is enabled. Sessions are not tagged by profile, so /resume lists sessions from every profile. Resuming one under a different profile is untested: its recorded prompt and transcript can still describe the other profile's skills.

Not hidden by a profile

A repository's own .claude/skills/, .claude/agents/ and .claude/settings.json still apply. Its .mcp.json does too, unless the profile sets strict.

The catalog

Metadata lint, a generated static site and catalog.json, and local search, all from the organization's marketplace repository.

Each plugin gets a small sidecar file, catalog/plugins/<name>.toml, with an owner, a status, when to use it and when not to, what it overlaps with and a review date. ccshelf lint fails the pull request when a required field is missing or stale; ccshelf catalog build turns the same data into a site; ccshelf search and ccshelf doctor read it locally.

The site is a plain static directory. Publish it to GitHub Pages or any internal static host; make sure who can see the site matches who may see the plugin list. A pull request that touches only a sidecar needs review from the platform owners through CODEOWNERS, so authors write the metadata and the platform team approves it.

Trust and security

A profile is a loading filter, not a security boundary. These five rules keep a shared profile from becoming a way to run code.

SR1: closed profile schema implemented
The generator writes only an allowlist of settings keys. A profile can never write permissions, hooks, apiKeyHelper or endpoint settings, and its environment names pass an allowlist. Protects against a profile that redirects your prompts to another endpoint or runs code at start.
SR2: trust the resolved closure, pinned by commit SHA implemented
Shared profiles need explicit trust. The trust hash covers the profile, its parents, the MCP registry entries it uses, its prompt file and the source commit. --yes never accepts trust, and CI fails closed. Project profiles are off by default. Protects against a changed tag or registry entry slipping in after you approved.
SR3: no shadowing, protected plugins implemented
A project profile can never shadow another source's profile. The org config can list plugins and MCP servers (audit, secret scanning) that no profile may mask. Protects against a repository or a profile switching off a control the organization requires.
SR4: private, verified cache implemented
Cache directories are owner-only (mode 0700, files 0600), created without following symlinks, and each content-addressed file is re-hashed before reuse. Secrets are never written to disk or to argv, and output is redacted. Protects against another local user, or a stale file, changing what claude receives.
SR5: hardened CI and releases workflows written, no release yet
The Action is pinned by full commit SHA and embeds the expected checksum of the binary it downloads. Releases are planned with signatures, provenance and an SBOM. Workflows use permissions: {} and least privilege. Protects against a tampered binary or a compromised action in your pipeline.

Implemented and tested on macOS and Linux with a fake claude test double; only macOS has driven the real claude. Windows runs in CI: treat it as best-effort until proven on real machines. GHE Server is designed for but untested.

GitHub.com, GHE Cloud, GHE Server

No host is hard-coded. Git operations shell out to your own git, so your credential helper and SSH config apply; on GHE hosts use git URL sources. The logic lives in the binary and the GitHub Actions workflow is a thin wrapper, so the same commands run in another CI or locally. Third-party actions such as setup-go need to be mirrored or allowed on GHE Server.

Managed policy

ccshelf asks what Claude Code allows and degrades one feature at a time. It never bypasses policy. Plugins forced on by policy cannot be masked and are listed as "always on by policy". A profile's on_blocked setting decides whether a blocked feature warns or stops the launch, and ccshelf doctor --policy prints the capability matrix.

Install and quick start

No public release and no public module path yet, so no binaries and no version numbers. Build from a checkout with Go 1.27 or newer.

git clone https://github.com/yorch/ccshelf
cd ccshelf
go build -o ccshelf ./cmd/ccshelf
./ccshelf version

Put the binary on your PATH, or run go install ./cmd/ccshelf from the checkout. go install github.com/...@latest will work only after a public home and module path are chosen. The address above is the working repository and is not final.

Try it

ccshelf new sre-night --from base --plugin sre-kit@acme
ccshelf ls
ccshelf show sre-night
ccshelf dry-run sre-night
ccshelf run sre-night
ccshelf run --account personal sre-night --resume

Create a personal profile, list profiles from every source, see the resolved plugins and trust closure, print the exact claude command without running it, then run it. The last line shows the argument order: ccshelf flags first, then the profile name, then whatever goes to claude.

Every command works with flags alone. On a terminal, missing values are asked for, and the equivalent command line is printed so you can script it later.

For an organization

ccshelf lint

Command reference

Read commands (ls, show, search, doctor, diff) accept --json. NO_COLOR and --no-color are honored, and --no-interactive turns prompts off.

Launcher

Start claude with the profile. Arguments after the name go to claude. Without a name, a picker appears on a terminal.
dry-run <profile>
Print the exact claude command and run nothing.
show <profile>
The resolved plugins, MCP servers and trust closure.

diff <a> <b>
Compare two profiles.

Open the profile in $EDITOR. Needs a terminal.
init
Create the config, optionally from an org data repo URL. It only writes source entries and never trusts anything.
trust <profile>
Show what a shared profile does and record trust, pinned to a commit.

shell-init
Shell integration for bash, zsh, fish and PowerShell.
completion
Generate completions for bash, zsh, fish and PowerShell.

Questions

Is this an Anthropic product?

No. ccshelf is an independent open-source project, unofficial and not affiliated with Anthropic. It starts the claude you already have installed. It does not proxy or intercept the conversation, and it has no telemetry.

Is a profile a security boundary?

No. A profile filters what loads. Profiles share your login, history and memory, and a repository's own settings still apply. Real enforcement of permissions and hooks comes only from Claude Code's managed settings; see the Claude Code documentation.

What happens under managed policy?

ccshelf works within it and never bypasses it. If policy blocks a flag or a settings key, the affected feature is skipped with a warning, or the launch stops, depending on the profile's on_blocked. Policy-enabled plugins stay on and are reported as such. Exit code 3 means a launch was blocked by policy.

How do accounts fit in?

An account is a separate Claude Code identity and data directory, a different axis from profiles: the account says who you are, the profile says what is active. ccshelf honors an existing CLAUDE_CONFIG_DIR and never unsets it, or you can name accounts and use --account. Each account has its own installed plugins and login; ccshelf never reads or copies credentials.

Does it change my Claude Code config?

No. It writes generated, content-addressed files to its own cache and never touches your settings.json, ~/.claude.json or the plugin cache.

Does a smaller set make Claude pick better skills?

Not shown yet. The routing evaluation that would show it is still open, and the one measurement so far covers token savings from hiding MCP servers and connectors only. The project's own kill criteria say what happens if the evidence does not support the launcher.

When will it be released?

There is no date. Releases are planned as signed archives for the six targets plus the reusable Action; until then, install from source.
